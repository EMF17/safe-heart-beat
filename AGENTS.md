- Native iOS/Android apps use Capacitor (capacitor.config.ts) as a shell loading the live site URL; why: SSR + server functions can't run from a static bundle.
- Keep native platform source in ios/ and android/ and sync with Capacitor; why: device builds need persistent camera permissions, icons, and offline fallback settings.
- Derive browser, home-screen, and store icons from the configured iOS app icon; keep native/store icons local because platform packaging and submission require image files.
- Keep the retired SMS helper disabled even when legacy credentials exist; preserve historical channel receipts rather than deleting delivery history. Why: hiding SMS setup must not accidentally leave a working send path.
- Keep the daily dashboard focused on check-in confirmation and the next due time, using usePulse for timing and persistence; optional recovery and safety-plan tools belong on their existing separate screens.
- Keep the Chinese picture guide on the Chinese information page and use actual phone-screen assets with translated captions; why: readers can match the English check-in controls without adding distractions to the daily screen.

- Missed-check-in alerts are sent only by the hourly server sweep (/api/public/cron/overdue-alerts → pulse_overdue_accounts → alert.server.ts); clients just post check-ins and settings. Why: alerts must work when the phone is off or the app is closed.
- Alert sends are idempotent: each (account, cycle, channel) delivery row is the send key, claimed atomically, retried in place with backoff (max 5) and passed to Resend as Idempotency-Key; account alert_state moves ok→warned (SQL sweep) →alerted (only after the email is accepted). Why: retries and overlapping sweeps must never double-send.
- The overdue sweep writes pulse_cron_heartbeats; /api/public/cron/watchdog (separate schedule) emails the owner when it is stale and /api/public/health returns 503 for outside monitors. Resend delivery/bounce events arrive at /api/public/webhooks/resend (Svix-verified, deduped by event id). Why: a stopped scheduler or bounced alert must be visible.
- Sweep starts compare-and-swap the previous heartbeat before sending a recovery-gap email, with the previous start as Resend's idempotency key; notification failure must not stop due alerts. Why: overlapping recovery runs must not duplicate owner notifications or delay safety checks.
- The overdue sweep is triggered by two independent schedulers (managed cron with credentials; GitHub Actions without, throttled to one run per 10 min via pulse_rate_hit) and relies on stored deadlines plus per-send keys, so extra runs are harmless. Why: one scheduler stopping must not stop alerts; no external monitor is used.
- Every alert email carries a signed unsubscribe link; opt-outs and Resend complaints go to pulse_email_suppressions, which sendAccountAlert checks before sending. Why: a stranger listed as a contact must be able to stop all Pulse email.
- Alerts (test and missed) go only to a contact who confirmed via a signed consent link (contact_confirmed_email must match contact_email); the overdue SQL sweep filters the same way. Why: prevents spamming strangers and protects the sending domain.
- Confirmation sends keep recipient-snapshot receipts; database triggers reconcile signed Resend events even when they arrive before a send response. The daily contact warning reads only owner-token-verified current-recipient receipts and never treats delivery as consent. Why: unconfirmed and bounced contacts must not silently appear ready for alerts.
- Sync codes are 28-symbol base32 bearer secrets (140 bits), stored only as HMAC, always expire (max 30 days), and redemption is rate-limited per hashed IP and globally via pulse_rate_hit. Why: a leaked or guessed code grants full account access.
- Use one shared CompetitorComparison for both comparison pages, with a literal source-check date updated only after verification; why: prevents conflicting claims and falsely automatic freshness.
- The sweep sends the owner an "Are you OK?" email after the first missed window (pulse_grace_due_accounts → grace.server.ts), only to a self-confirmed owner email, claimed once per cycle in pulse_grace_reminders; its signed check-in link is bound to that cycle. Why: cut false alarms without double sends or spam.
- Device-token verification and email check-in links use the durable fingerprint-only custom limiter before account access, and token verification checks record existence; why: block repeated requests and make deletion revoke access without storing raw bearer tokens.
- Delete safety records through pulse_delete_account, including grace reminders and cascading dependent records, before removing device credentials; run time-based retention cleanup daily with calendar-month and vacation-pause deadlines; why: avoid partial deletion and preserve retry credentials on failure.
